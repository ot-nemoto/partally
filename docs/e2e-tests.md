# E2Eテスト一覧と検証結果

partally に必要な E2E（ブラウザを通した）テストの一覧と、実環境で試した結果をまとめる。機能のルールは [機能仕様書](spec.md)、開発の手順は [開発ガイド](development.md) を参照。

E2E は `e2e/tests` に Playwright で実装している（#193）。今は P0 の 12 本を `e2e/tests/p0.spec.ts` に、P1 のうち実装したもの（「実装済み」と書いたもの）を `e2e/tests/p1.spec.ts` に、P2 のうち実装したものを `e2e/tests/p2.spec.ts` に、ゲーム（P1・P2。テスト名の頭に `P1`・`P2` を付ける）を `e2e/tests/game.spec.ts` に、3 章「公開・設定・移行・言語・景品・スケジュール」と、それにかかわる P2 を `e2e/tests/settings.spec.ts`（参加者への公開・ポイントの設定・景品・ゲームの結果・Trend）・`e2e/tests/schedule.spec.ts`（スケジュール）・`e2e/tests/data.spec.ts`（データの移行）・`e2e/tests/screens.spec.ts`（言語・スマホの幅・以前の URL・QR の印刷・XSS）に、CSP を効かせた確認（5 章）を `e2e/tests/csp.spec.ts` に置き、`npm run e2e` で実行する。CI（`.github/workflows/ci.yml`）の `e2e` ジョブでも実行し、通らないと本番へデプロイしない。P1・P2 の残りは未実装。

## 1. 前提：既存テストとの分担

E2E 以外の自動テストは次の範囲をカバーしているため、E2E では重複させない。

| 既存テスト | カバー範囲 |
|---|---|
| `api/src/app.*.test.ts` | 認証（1 台の端末で複数の参加者を含む）・管理者ログインの制限と Cookie・写真（アップロードの上限を含む）・お気に入り・ゲーム6形式・ラウンド・景品・スケジュール・イベント終了・CloudFront を通ったかの確かめ・CSP の報告の API 統合テスト（メモリ内リポジトリ） |
| `infra/test/*.test.ts` | CDK のスタック（リソース・応答のヘッダ・権限）と、ワークフローの決まり（アクションの指定の仕方など） |
| `api/src/scoring.test.ts` | ポイント・順位・同点処理の計算 |
| `packages/shared/src/*.test.ts` | game-rules、景品の順位、データ移行の ZIP（data / prize / game archive、schedule-file） |
| `web` の単体テスト | StatusFilter と i18n のみ（画面の流れは E2E で確かめる） |

E2E の対象は、API テストでは検証できない次のものに限る。

1. 実ブラウザの画面遷移・表示・入力（SPA のルーティング、ダイアログ、ドラッグ操作）
2. 複数アクター・複数端末の連携（幹事の操作が参加者の画面にどう届くか、その逆）
3. Cookie・セッション・localStorage・IndexedDB などブラウザの状態
4. ファイルの実アップロード／ダウンロード（写真、景品・ゲームの画像、ZIP 移行、QR 印刷）
5. 時間・ポーリング依存の挙動（ゲーム開催の5秒ポーリング、スケジュールの「いま／つぎ」の30秒更新、写真の30秒再送）
6. オフライン・通信断からの復旧

優先度は、P0 = イベント当日に壊れると進行が止まる、P1 = 主要機能の連携、P2 = あると安心、とする。

## 3. P1：主要な連携（約44本）

各見出しの Issue で実装する（実装済みのものは見出しか行に書いた）。

### 参加・認証（#267）

- 無効な QR トークンでは登録に進めない
- 暗証番号を5回間違えてロック → 幹事が解除すると別端末でログインできる（ログイン中の端末は使える）
- 紐づけ解除 → 解除された参加者は次の操作でログアウトし、同じ QR で新規登録できる（ポイントは引き継がない）。その端末でほかの参加者も覚えていれば、ログアウトせずにその人に切り替わる
- 未ログインで参加者・管理画面の URL を直接開くと、それぞれ案内・ログインへ戻る
- LINE などのアプリ内ブラウザで開くと、標準のカメラで読み込むよう注意文が出る（`QrLanding.tsx` の `InAppBrowserNotice`。userAgent を変えて確かめる）
- 紐づけを解除した人は、管理画面のランキングで薄く出る。参加者のランキングと景品の順位には数えない（2 章・G-3）

### 1 台の端末で複数の参加者（U-9。最後の 1 本のほかは `e2e/tests/p1.spec.ts` で実装済み）

- 同じ端末で 2 人を登録すると、上に名前のボタンが並び、今の人に色が付く。押すとその人に切り替わり、ホーム以外の画面（みんなの写真）でも同じ画面のまま切り替わる。覚えている人の QR を読み込むと、暗証番号を聞かれずにその人になる
- 送信待ちの写真は、ほかの人に切り替えた後に送られても、撮った人の写真になる
- 使っていない人の紐づけを解除してからその人のボタンを押すと、案内が出てボタンが消える。使っている人の紐づけを解除すると、画面を開いたまま覚えているほかの人に切り替わり、残りが 1 人ならボタンが消える
- 端末に覚えるのは 5 人までで、6 人目がログインすると、いちばん前にログインした人が外れる（未実装。#267）

### 写真のアップロードの上限（`e2e/tests/p1.spec.ts` で実装済み）

- 確認待ちが上限（30 枚）に達した参加者が送ると、写真は送信待ちに残り、確認待ちの案内が出る。自動の送り直しで断られ続けても送信の失敗に数えず、写真を捨てない。幹事が承認して上限を下回ると、次の送り直しで送られる
- 短い間（10 分の区切り）に枠を取りすぎると、写真は送信待ちに残り、少し待ってから送る案内が出る（区切りが変わってからの送信は、時間を待たないと確かめられないので API のテストに任せる）

準備の確認待ちの写真は、ローカルの S3 の代わり（`/__dev/upload`）へ直接置いて作る（枠を取らないので、区切りの上限に数えない）。送り直しの間隔（60 秒）は、画面の時計（`page.clock`）を進めて待たずに確かめる。

### 写真・お気に入り（#268）

- HEIC の写真を投稿できる（変換に失敗したときは元の画像を送らずエラーを出す）。`e2e/tests/p1.spec.ts` で実装済み：HEIC を読めない Chromium で、heic2any で JPEG に変換されて送られ、ギャラリーに元の大きさで出ること。読めない HEIC は送らずに案内が出ること
- 大きい写真が縮小され、一覧（サムネイル）と拡大（本体）で表示される
- オフラインで投稿 → 送信待ちがホームに出て、オンラインに戻ると自動で送られる（「今すぐ再送」でも送れる）
- 即時公開（設定 `post`）では承認なしで公開されポイントが入る。切り替えは後の投稿にだけ効く
- 却下 → 投稿者に「非公開」と出る。公開中の写真を削除 → 自分の写真からも消え、お気に入りとポイントが戻る
- 確認待ちの写真は、投稿者本人と幹事以外には見えない
- 送った写真から、位置情報などの撮影情報が消えている（3 章）
- お気に入りの受付をオフにすると、付けることも外すこともできない。付いた分は残る（F-5）
- お気に入りの上限に達すると、新しく選べない。自分の写真には ♡ が出ない（F-2・F-3）

### ゲーム共通・形式別・ラウンド（`e2e/tests/game.spec.ts` で実装済み。共通・ラウンドは #269、形式別は #270）

- 開催中は別のゲームを開始できない（1問とラウンドで共通）（実装済み）
- 中断しても答えは残り、再開始しても答え直しできない（実装済み）
- 終了を取り消すとポイントが消え、もう一度終了するとその時刻で入り直す（実装済み）
- 参加者が画面を開いたまま、開始でお知らせが出て、終了で消える（再読み込みなし）（実装済み）
- 数値予想：正解の数を入れないと終了できず、理由が出る。終了後は近い順の点数と「2位（予想42）+5」の形でホームに出る（実装済み）
- 投票：名前・二つ名で絞り込め、自分には投票できない。参加者には票数と投票先が見えず、幹事には集計が見える（実装済み）
- 合言葉：不正解なら何度でも試せる。表記ゆれ（パーティー／ぱーてぃー）でも正解になる。正解後は送れない（実装済み）
- 抽選：「参加する」は1回だけ。終了で当選が決まり、終了の取り消しでは引き直しの注意が出る（実装済み）
- ラウンド：開始するとお知らせに「N問中M問回答済み」が出て、全問が番号順に並ぶ。1問ずつ答え、一括で終了すると全問同じ時刻でポイントが入る。ラウンドの中のゲームは単独で開始・終了できない（実装済み）
- ラウンドの管理画面の操作：作る、ゲームの出し入れと出す順の並べ替え（「↑」「↓」）、ラウンドの並べ替え（「↑」「↓」）。ラウンドを消しても中のゲームは残る（実装済み）
- お知らせの文言が形式ごとに出る（「投票受付中」「合言葉を受付中」「抽選の参加受付中」「ゲーム開催中」）（K-3。実装済み）
- 抽選：幹事の画面に当選者が順番どおりに出て、抽選に入らなかった人も出る。参加者のホームに「1 等に当選 +30」の形で出る（L-3。実装済み）

### 公開・設定・移行・言語・景品・スケジュール（#271。すべて実装済み。どのファイルかは冒頭の段落を参照）

- ランキング・推移・景品・スケジュール・ゲーム結果の公開を個別に切り替えると、参加者の「イベント情報」の出し分けが変わる。オフのものは API からも返らない
- 名前を伏せる（全員 `???`）・ポイントを伏せる（数字なしで棒と線の形だけ）が参加者の画面に効く
- スケジュールのドラッグ編集（上下で開始時刻、下の端で長さ、左右で列）と、列の表示／非表示（非表示の列は参加者に出ず、「いま／つぎ」も表示項目だけで決まる）
- ポイントの点数を変えると、全員の表示ポイントが再計算される（ホーム・ランキング・幹事のユーザ一覧で一致する）
- ポイントを伏せる／ゲームの点数を伏せる設定がホームに効き、幹事には見える

## 7. 実装の作り

2026-11-19 の試行（8章）から得た決め事と、それに沿った今の作り。

- 道具は Playwright（`e2e` ワークスペース、`@playwright/test`）。幹事と参加者A・Bを別々の BrowserContext で同時操作でき、モバイル幅・オフライン・ダウンロードの検証が1つで足りるため。参加者はスマホの大きさ（390×844）、幹事は PC の大きさで開く
- ふだんはローカル開発環境（メモリ内の API `api/src/dev.ts` と web の Vite）に対して実行する（CI も同じ）。データの入った環境へ向けるときは「データの入った環境へ向けて流す」を参照。`playwright.config.ts` の `webServer` で両方と、CSP の確認に使う本番と同じビルドの画面（`vite preview`、ポート 4173）を起動する（API と Vite は、手元で起動済みなら使い回す。`vite preview` は古いビルドで確かめないよう、毎回ビルドし直して起動する）
- API は1つで、データはテストの間で共有する。そのためテストは1つずつ順に実行し（`workers: 1`）、各テストは自分で作ったデータだけを見る。開催中のゲーム・ラウンドは、テストのたびに `afterEach` で止めて次のテストに持ち越さない
- 準備（QR の発行・参加者の登録・ゲームの作成・設定の変更）は API を直接呼んで作り、検証したい流れだけを画面から操作する。`e2e/tests/helpers.ts` の `adminApi()`（幹事の API）・`participant()`（登録済みの参加者のブラウザ）・`adminPage()`（ログイン済みの幹事のブラウザ）・`updateSettings()` を使う
- 設定は、各 spec の初めに `useDefaultSettings()` で既定値（`api/src/repository.ts` の `DEFAULT_SETTINGS`）にそろえる。テストの中で `updateSettings()` で変えた設定は、テストのたびに既定値へ戻し、spec の終わりに始める前の設定へ戻す
- 画面で名前を使って探すデータ（ゲーム・景品・スケジュールの項目・ランキングの参加者）は、`unique()` で実行ごとに変わる名前にする。前に流したときのデータや、同じ名前のデータがあっても、1 つに決まるように
- スケジュールの「いま」「つぎ」を確かめるテストは、参加者の画面の時刻を `page.clock` で決める（流した時刻で変わらないように）。「つぎ」は、今の時刻の 1〜2 分後に始まる項目で確かめる（その時刻に始まるほかの項目があっても、同じく「つぎ」になるだけで、確かめる項目の表示は変わらない）
- スケジュールは 1 つの時間軸を共有する。項目は列 49（作ると右端の新しい列になる）に置いてほかの項目と同じ列にせず、作った項目はテストの終わりに `deleteScheduleItems()` で消す（残すと、同じ時刻に流すたびに列が増え、上限の 50 列に届く）
- 幹事の画面で写真を承認するテストは、自分の写真のカードを選ぶ（ほかの人の確認待ちの写真があってもよいように）
- 確認ダイアログは、画面内の確認ダイアログ（`web/src/components/ConfirmDialog.tsx` の `confirmDialog()`）で出す（#194 で `window.confirm()` から置き換えた）。テストでは `acceptConfirm()` で「OK」を押し、確認を承認して進む流れとして確かめる
- 写真・景品の画像は、実ファイルのアップロードで検証する。画像は `jpeg()` でブラウザの canvas から作る。HEIC は `e2e/fixtures/sample.heic` を使う（`e2e/fixtures/make-heic.py` で ffmpeg から作ったもの。外から見本を持ち込まない）
- CI では `e2e` ジョブで Chromium を入れて実行し、失敗したら HTML のレポートを成果物として残す

### データの入った環境へ向けて流す

検証用の本番相当の環境など、データの入った環境へ向けて流すときは、`E2E_BASE_URL` にその環境の URL（ホストまで。パスは付けない）を、`ADMIN_PASSWORD` にその環境の管理者パスワードを入れる。イベントで使っている環境（当日や、参加者がいる間）には流さない（下の注意のとおり、設定・ゲーム・イベントの終了を動かすため）。

```sh
E2E_BASE_URL=<環境の URL> ADMIN_PASSWORD=<管理者パスワード> npm run e2e
```

- `E2E_BASE_URL` を付けると、ローカルの API・web・`vite preview` を起動せず、その URL の画面と API を使う。CSP のテスト（5章）も、その環境の画面（本番と同じビルド）に CSP を付けて開く
- 次の 2 本は、ローカルでしか確かめられないので skip する
  - P1「確認待ちが上限に達すると…」：確認待ちを埋めるのに、ローカルの S3 の代わり `/__dev/upload` を使う
  - P2「管理者ログインを続けて間違えると…」：接続元のヘッダ（`cloudfront-viewer-address`）を偽って、このテストだけの接続元にする。CloudFront を通すとヘッダは閲覧者の IP で付け直されるので、流した回線の管理者ログインが 15 分断られる
- 流した環境には、テストが作った参加者・QR コード・ゲーム・ラウンド・景品・写真が残る（スケジュールの項目のほかは、テストは消さない。データの移行のテストは、作ったゲーム・景品を取り込んで増やす）。流した後は初期化する前提で使う（[初期設定・デプロイ手順](setup.md#本番データの初期化)）
- 流している間は、設定が既定値に変わる（終わったら戻す。途中で止めたときは戻らないことがある）。開催中のゲーム・ラウンドは止まり、イベントの終了も一時的に行う
- イベントが既に終了している環境では、P0-12 を skip する（最後の取り消しで、その環境の終了の記録を消さないように）

### 試行で分かったこと

- **自動操作で進めなかった操作は、どれも `window.confirm()` で確認するもの**だった（ゲームとラウンドの終了・中断・取り消し・削除、イベントの終了・取り消し）。自動操作ではダイアログもモーダルも表示されず、エラーも出ず、状態が変わらなかった。コードでも、確認が通らなければ処理を中断して API を送らない作りになっている（`web/src/pages/admin/AdminGames.tsx`、`AdminSettings.tsx`、`games/Rounds.tsx`）。手動ではすべて正常に動いたため、アプリの不具合ではないと判断した。改修の Issue は #194（対応済み。画面内の確認ダイアログに置き換えた）
  - ただし QR の発行も `confirm()` で確認する（`AdminTokens.tsx`）のに、試行では自動操作で発行できている。`confirm()` だけが原因とは言い切れず、QR の発行で確認がどう扱われたか（ダイアログが出て承認されたのか）は確かめていない。#194 の置き換え後は、E2E では画面内の確認ダイアログで「OK」を押して進む
  - `confirm()` はほかに、ユーザの紐づけ解除・暗証番号のロック解除・消去（`AdminUsers.tsx`）、写真の削除（`AdminPhotos.tsx`）、景品の削除（`AdminPrizes.tsx`）、スケジュールの項目の削除（`AdminSchedule.tsx`）、データの取り込みの確認（`data/DataImportDialog.tsx`）で使っている。試行では触っていないが、同じく自動操作では止まるおそれがあったため、#194 でまとめて置き換えた
- **管理画面の一覧が、保存や操作の直後には古いまま**。ゲームの回答数（「更新」を押しても変わらず、再読み込みで変わった）、作成した景品とスケジュールの項目（再読み込みで出た）で確認した。Issue は #195（対応済み。一覧の読み込みが追いつくまで、保存した内容を画面に重ねて出す）
